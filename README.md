# 自适应 Goal 与循环编译器

**duke ｜ 联系与交流：微信公众号 Dukeland**

这是一个为 Codex `/goal` 和自主 Agent 编写执行提示词的 Skill。给它任务、现有材料和你已经定下的边界，它会产出一段指令，说明要交付什么、怎样判断做成了，以及哪项验收失败后该回去做什么。

假设报名系统只剩一个名额，两个人同时提交，系统却都显示报名成功。给这个任务写 Goal，可以要求执行者先在测试环境复现并发提交，修复后用同样的方式重试，再查报名记录。两次提交里应有一次成功，数据库也只应新增一条有效记录。

[查看完整 Skill](./adaptive-goal-loop-designer/SKILL.md) · [开始使用](#开始使用) · [使用示例](#使用示例)

## 开始使用

1. 下载或克隆本仓库。把 [`adaptive-goal-loop-designer/`](./adaptive-goal-loop-designer/) 整个目录放进项目的 `.agents/skills/`，或放进个人的 `~/.agents/skills/`。如果列表里没出现，重启 Codex 后再查看。其他支持 Skill 的工具按各自的目录约定安装。 [Codex Skills 文档](https://learn.chatgpt.com/docs/build-skills#where-codex-loads-local-skills)
2. 在对话里选中或点名 `$adaptive-goal-loop-designer`，说明你想完成的事、已有材料的位置，以及哪些内容可以改、哪些条件必须保留。有明确的失败记录或验收用例，也一起给它。
3. 把生成的完整提示词交给能读取这些材料的执行 Agent。在支持 Goal 模式的 Codex 会话里，用 `/goal` 设置这段目标。普通对话也可以直接接收这段提示词，持续执行的方式取决于所用环境。 [Codex `/goal` 文档](https://learn.chatgpt.com/docs/reference/slash-commands#set-or-manage-a-goal-with-goal)

普通聊天工具也可以用来写 Goal。把 [`SKILL.md`](./adaptive-goal-loop-designer/SKILL.md) 全文和你的任务说明一起发给模型，再把它生成的目标交给执行者。

## 怎样把任务写成 Goal

### 先查会改变任务的未知

Skill 会先看任务说明、上游规格、现有成品和失败记录。比如接到「把报告改到能送审」，它需要确认读者是谁、核心论点能否调整、证据材料在哪里。资料里已有答案的就直接使用。必须由你决定、且会改变成果或授权的问题，才集中询问。执行者可以自行选择可逆的实现办法，提示词只保留需要贯穿全程的约束。

### 让验收结果决定下一步

Skill 所说的「循环」，指一次工作完成后，检查实际结果，再根据发现的问题决定下一轮。研究时，一份可靠的反例可能要求缩小结论。修功能时，复现用例失败就要找原因、改实现、重跑用例。任务不同，验收对象和返工动作也随之变化。

| 任务 | 拿什么验收 | 发现问题后怎么继续 |
| --- | --- | --- |
| 成品优化 | 稿件全文、可运行页面、完整视频等实际成品 | 修具体段落、页面或片段，回看改动对整体的影响 |
| 发现与选择 | 同批候选和低成本验证结果，以及可投入的时间、预算或人力 | 淘汰站不住的候选，给有希望的候选补证据 |
| 研究与证伪 | 能复核的来源、关键反例和可能成立的其他解释 | 追查关键证据，修正假设或缩小结论范围 |
| 构建与验证 | 可复现的用例、实际运行结果和数据核验 | 定位失败、修复、重跑相关检查 |
| 策略竞争 | 各方向在受众、渠道和资源条件下的可行性，以及深化后的完整方案 | 淘汰无法成立的方向，验证最有希望的方向能否落地 |

标杆要用在可比较的地方。重写一篇特稿，可以找同阶段、同形态、同用途的全文作参照。编辑要在五条线索里选一条时，成熟报道可以帮助校准编辑的判断，最终还是要比较这五条线索各自的证据和可做性。测试本身足以裁决的功能任务，直接跑测试即可。

### 把条件写进一段可执行的提示词

生成的 Goal 会写明一个主要目标、必须读取的材料、硬边界、自主权限、工作循环、验收证据和停止条件。通常写成 500～1500 个中文字符，复杂技术任务可延长到 2200 个字符。现成规范用路径或链接指明，执行者必须能打开它们。

交付前，Skill 会预演两轮。第一轮看执行者能否按字面要求过早交差，比如只跑了单人报名就宣称并发问题已经修复。第二轮看验收指出遗漏后，提示词是否要求它补跑并发用例、修实际问题，再给出结果。关键输入或权限确实缺失时，交付已完成的部分，说明哪项验收还需要什么。

## 使用示例

以下示例使用假设场景，使用时把材料名和边界换成执行 Agent 实际能访问的内容。

### 修复报名系统的并发超额

可以这样请 Skill 写 Goal。

```text
用 $adaptive-goal-loop-designer 帮我写一条 Goal。活动只剩一个名额时，两个并发请求都可能报名成功。仓库里有报名接口说明和原有测试，可以改服务端和相关测试，接口返回约定照旧。只在测试环境操作。
```

生成的 Goal 可以这样规定复现和验收。

```text
修复活动只剩一个名额时的并发超额问题。读取仓库里的报名接口说明和相关测试。可修改服务端和相关测试，保留现有接口约定和验收要求，只在测试环境操作。

用两个独立的报名请求同时争抢最后一个名额，保存修复前的复现结果。修复后重跑同一场景，确认恰有一个请求成功，另一个按已满处理，且数据库只新增一条有效报名。随后运行正常报名和已满拒绝的相关回归用例。检查失败时定位并修复实际问题，再重跑受影响的用例。

交付修改和上述验证结果。如果复现依赖缺失，给出能确认的范围、已完成的工作和缺少的环境条件。
```

### 核对图书馆延时开放的实施范围

这类研究的重点是厘清各馆点目前有证据支持的状态。可以给执行者这样的 Goal。

```text
根据项目里的试点公告、馆点名单和资料截止日期，查明各馆点周末延时开放安排的生效范围。交付一份可复核的短报告，列出具体馆点、适用日期、开放时段和对应来源。使用可公开核查的资料。

从试点公告提出暂定范围，逐馆核对最新的开馆时间和临时调整公告。如果总公告和分馆通知冲突，检查各自的生效日期、适用馆点和后续更新，据此修正结论。证据只支持计划的馆点保留计划表述。来源仍冲突或找不到有效时段的馆点，说明当前能确认到哪一步。

核查结果应足以让读者从每条主要判断追到原始来源。馆点和日期都核过后交付。确有资料缺口时列出受影响的馆点、已查证据和待确认事项。
```

## 使用边界

一次性的小改动通常只需要说明交付和验收。多轮工作更值得用这套 Skill，尤其是各轮会遇到不同的失败、需要靠真实证据决定下一步的时候。

主观质量需要具体的参照。要把一篇文章改得更接近作者的声音，可以提供作者认可的全文和具体审读反馈，最终仍要通读成稿。需要独立评审时，要确认执行环境能提供与生产者独立的评审者，并具备相应授权。只有主 Agent 可用时，按自审设计即可。

实际效果取决于任务的材料、验收标准和执行环境。Goal 可以说明什么证据才算过关，核对证据、运行测试和修改成品仍由执行者完成。
